# 来源策略

## 来源类型

| 类型 | 用途 | 不能单独证明 |
|---|---|---|
| 当前事件 | 当前现象、影响和现场事实 | 产品普遍行为 |
| 正式产品资料 | 发布能力、规格和操作说明 | 具体代码实现 |
| 版本公告 | 发布范围和版本边界 | 当前现场根因 |
| 对应版本源码 | 机制、条件、错误文本和合入事实 | 商业承诺、发布包实际包含 |
| Jira | 已知缺陷、跟踪状态和计划版本 | 已发布、当前事件根因 |
| BBS | 历史案例和可复用排查动作 | 当前事件根因 |
| Confluence | 研发设计和内部说明 | 正式产品承诺 |
| 外部官方资料 | 第三方组件机制 | ZStack 当前事件事实 |

## 冲突处理

- 正式资料与代码冲突：明确列出差异，转产品或研发确认。
- Jira 声称已修复但目标 commit 不含修复：不得写目标版本已修复。
- BBS 案例与当前事件信号不一致：只保留为排除项或参考。
- 查询失败与零命中分开记录。

## 版本约束

依赖版本的断言必须绑定产品版本或 CodeContext。未标版本的资料不自动继承当前问题版本。

## 证据成熟度

内部分析对关键断言使用以下等级，来源类型与成熟度分开记录：

- `E0`：没有可核验依据。
- `E1`：存在一般资料或相似案例，尚未映射当前问题。
- `E2`：多项参考证据一致，但缺当前事件或目标版本直接证明。
- `E3`：正式资料、对应版本源码或已知问题记录直接支持。
- `E4`：直接证据已与当前事件现象、版本和对象完成映射。
- `E5`：处理完成，并由当前事件的恢复验证和观察结果闭环。

不得因为 Jira 标记已解决、BBS 有相似案例或代码存在修复就使用 `E5`。

来源类型不能由模型标签单独证明。外发 URL 只允许答案门禁中的批准 host；生产网关还必须从连接器结果生成不可由模型修改的 provenance ID，并在发送时复核来源类型、URL 和采集时间。`answered + complete` 至少需要一个批准来源。
